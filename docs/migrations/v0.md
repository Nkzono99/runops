# v0 Migration Guide

v0 系は pre-public な開発期間です。後方互換 layer を長く維持するよりも、project
ごとに移行手順を明示して素早く設計を改善する方針です。

この guide は `0.x` の runops へ更新するときに確認します。該当しない item は
`not applicable` として扱い、必要なものだけ `migrate-runops` で適用します。

## M0-0001 Analysis artifact indexes

- Since: 0.7.0
- Type: compatible-generated
- Impact: analysis-artifact
- Applies when:
  - project に `runs/<run>/analysis/` または `runs/<survey>/summary/` の解析成果物がある。
  - 後続 Agent が figure / CSV / Markdown summary / script の意味を復元しにくい。
- What changed:
  - analysis artifact を一級市民として扱うため、run-local 解析は
    `runs/<run>/analysis/artifacts.toml`、survey / cross-run 集計は
    `runs/<survey>/summary/artifacts.toml` に index を置けるようになった。
  - `kind`, `path`, `title`, `script`, `data`, `description`, `status` を中心に、
    成果物の意味と provenance を軽く記録する。
- Migration:
  - CLI で確認する: `runo migrate apply M0-0001 --dry-run`
  - CLI で適用する: `runo migrate apply M0-0001`
  - 既存の解析成果物はそのまま有効。必須 migration はない。
  - active な run / survey だけ、次回の解析時に `runo analyze summarize` または
    `runo analyze collect` を再実行して `artifacts.toml` を生成する。
  - 既存 `analysis/summary.json` や `summary/survey_summary.*` から index だけを
    補完する場合は、上記 CLI migration を使う。
  - 手作業で index を補う場合は、成果物の隣に置き、相対 path で `path`,
    `script`, `data` を書く。
- Validation:
  - `artifacts.toml` 内の `path` が実在する。
  - note / report から figure や CSV を参照するとき、同じ成果物が
    `artifacts.toml` にも載っている。
  - `runo analyze` 系 command が対象 run / survey で失敗しない。
  - `runo lint --scope analysis` が対象 artifact index の不足を報告しない。
- Rollback:
  - `artifacts.toml` は index なので、削除しても元の解析成果物は失われない。
- Human gate:
  - 不要。大量の古い run に対して一括再解析する場合だけ、人間に scope と cost を確認する。

## M0-0002 Research agenda in context

- Since: 0.7.0
- Type: compatible-generated
- Impact: research
- Applies when:
  - project に `research/agenda.md` がある、または `runo update-harness` で
    `research/` scaffold が補完される。
- What changed:
  - `runo context --json` が `research_agenda` summary を返し、Agent が最初に
    `research/agenda.md` の存在と現在判断の preview に気づけるようになった。
- Migration:
  - CLI で確認する: `runo migrate apply M0-0002 --dry-run`
  - CLI で適用する: `runo migrate apply M0-0002`
  - 必須 migration はない。
  - `research/agenda.md` がない既存 project では `runo update-harness` を実行し、
    scaffold された agenda を現在の研究判断に合わせて編集する。
  - `update-harness` を使えない状況で不足分だけ補完する場合は、上記 CLI
    migration を使う。既存 file は上書きしない。
- Validation:
  - `runo context --json` に `research_agenda.exists`, `path`,
    `current_decision_heading`, `next_actions_count` が含まれる。
  - `research/agenda.md` が TODO list ではなく mutable decision ledger として書かれている。
  - `runo lint --scope structure,knowledge` で agenda の不足を確認できる。
- Rollback:
  - 不要。
- Human gate:
  - agenda の現在判断を大きく書き換える場合だけ、人間に確認する。

## M0-0003 Remove legacy survey figure index

- Since: 0.7.0
- Type: breaking-generated
- Impact: analysis-artifact
- Applies when:
  - project に `runs/<survey>/summary/figures_index.json` がある。
  - `summary/artifacts.toml` に `path = "figures_index.json"` の旧互換 entry がある。
- What changed:
  - `runo analyze collect` は `summary/figures_index.json` を生成しない。
  - figure の索引は `summary/artifacts.toml` を正本にする。
  - `summary/survey_summary.json` には引き続き run ごとの `figures` 情報が入る。
- Migration:
  - CLI で確認する: `runo migrate apply M0-0003 --dry-run`
  - CLI で適用する: `runo migrate apply M0-0003`
  - 既存 `summary/figures_index.json` を削除する。
  - `summary/artifacts.toml` に残っている `figures_index.json` entry を削除する。
- Validation:
  - `runo analyze collect <survey>` を実行しても `summary/figures_index.json` が生成されない。
  - `summary/artifacts.toml` に figure artifact と summary outputs が残っている。
  - `summary/survey_summary.json` の各 run entry に必要な `figures` 情報が残っている。
  - `runo lint --scope analysis` が `analysis.legacy_figures_index` を報告しない。
- Rollback:
  - 旧形式が必要な場合は `summary/survey_summary.json` または `summary/artifacts.toml` から
    project-local script で一時生成する。
- Human gate:
  - 不要。削除対象は runops が生成した legacy index のみ。

## M0-0004 Experiment ledger schema 2

- Since: next v0 release
- Type: breaking-project-state
- Impact: research, experiment-ledger
- Applies when:
  - `research/experiments.toml` の `schema_version = 1` を使っている。
  - `runo experiment new/show/check` で型付き experiment workflow を使う。
- What changed:
  - ledger schema 2 は `title`, `question`, `cost_ceiling_core_hours` を持ち、
    full-stage authorization を構造化する。
  - phase は保存せず、ledger、survey、run manifest、artifact index から導出する。
  - legacy record で科学的情報を安全に補えない場合は推測せず
    `migration_blockers` に列挙し、実行 gate は fail closed する。
- Migration:
  - 確認する: `runo migrate apply M0-0004 --dry-run`
  - 内容を確認後に適用する: `runo migrate apply M0-0004 --yes`
  - migration は未知 field を保持し、保存済みの derived `phase` だけを除去する。
  - blocker を解消するには人間が `title`, `question`,
    `cost_ceiling_core_hours` を記録し、`migration_blockers` から該当項目を除く。
- Validation:
  - `runo experiment check` が error を報告しない。
  - `runo experiment show EXPERIMENT --json` が導出 phase と次の操作を返す。
- Rollback:
  - 適用前に Git または別 backup へ ledger を保存する。schema 2 を schema 1 へ
    自動 downgrade する migration は提供しない。
- Human gate:
  - 必須。migration 自体は科学的内容を生成しないが、project-state schema を変更する。

## M0-0005 Grouped CLI and internal application boundary

- Since: next v0 release
- Type: breaking-internal / compatible-cli-alias
- Impact: developer imports, scripts, Agent guidance
- Applies when:
  - script や文書が古い flat command (`runops submit`, `runops collect` 等) を使う。
  - project-local Python code が旧 `runops.core.actions`, `runops.core.run_creation`,
    analysis/publication/operator helper を import する。
- What changed:
  - preferred executable は `runo`、現行 surface は grouped command になった。
    例: `runo runs submit`, `runo analyze collect`, `runo runs archive`。
  - 確認省略は `--yes` が canonical。`runo update --force` は同一 semantics の
    **hidden** compatibility alias としてだけ残る。
  - 内部レイヤを `core/ -> application/ -> interfaces/infrastructure` に整理した。
    orchestration は `core/` から `application/` へ移り、MCP tool implementation は
    capability module に分割された。
- Migration:
  - shell script と Agent guidance を `.codex/rules/commands.md` の grouped `runo`
    command に置き換える。
  - internal Python import は次へ更新する。旧 internal path の compatibility shim は
    提供しない。
    - `runops.core.actions` → `runops.application.actions`
    - `runops.core.run_creation` → `runops.application.run_creation`
    - `runops.core.context` → `runops.application.context`
    - `runops.core.analysis` → `runops.application.analysis`
    - `runops.core.publication` → `runops.application.publication`
    - `runops.core.readiness` → `runops.application.execution.readiness`
    - `runops.core.retry` → `runops.application.execution.retry`
    - `runops.core.plugins` → `runops.application.gateway.plugins`
    - `runops.core.lint` → `runops.application.operator.lint`
    - `runops.core.migrations` → `runops.application.operator.migrations`
  - application 境界の移動だけでは manifest/project-state を書き換えない。未知
    manifest field も保持される。ただし、現行 `schemas/manifest.json` に対する
    validation と submit lock の ignore 設定は M0-0006 を確認する。
- Validation:
  - `uv run runo --help` と対象 grouped command の `--help` が成功する。
  - `runo runs submit --dry-run` と MCP submit plan が同じ command/precondition を返す。
  - project の `manifest.toml` bytes/field が internal import 移動だけで変化しない。
- Rollback:
  - code checkout を以前の v0 release に戻す。project-state rollback は不要。
- Human gate:
  - bulk submit など実際の外部操作を validation する場合のみ必要。

## M0-0006 Durable submit lock and strict manifest validation

- Since: next v0 release
- Type: breaking-schema / compatible-runtime
- Impact: existing project `.gitignore`, manifest validator, submission recovery
- Applies when:
  - 既存 project の `.gitignore` に `**/.runops-submit.lock` がない。
  - 以前の `schemas/manifest.json` では valid だった manifest を、現行 schema でも
    validation する。
  - run root に `pending` または `accepted:<job_id>` を含む
    `.runops-submit.lock` がある。
- What changed:
  - submit の process lock と durable claim は run root の
    `.runops-submit.lock` を共有する。この file は lock inode を安定させるため
    submit 完了後も空 file として残る内部 artifact で、Git 管理しない。
  - `schemas/manifest.json` は SPEC 12.3 の required table/field と型を厳密に要求する。
    したがって、旧 schema では valid だった manifest が現行 validator で invalid に
    なることは breaking な schema contract 変更である。
  - runtime の `read_manifest()` は v0 compatibility のため、required data が不足する
    旧 manifest も引き続き読み取る。通常の read/update では未知 field も保持する。
- Migration:
  - まず `runo update-harness --dry-run` で managed `.gitignore` の差分を確認し、
    `runo update-harness` で反映する。手動 merge する場合は project の
    `.gitignore` に次の pattern を追加する。

    ```gitignore
    **/.runops-submit.lock
    ```

  - `.runops-submit.lock` が `pending` または `accepted:<job_id>` を含む場合、scheduler
    の受付結果と `manifest.toml` の `run.status`, `job.job_id`, `job.submitted_at` を
    照合して reconcile する。照合・復旧が完了する前に lock file を unlink、truncate、
    または空文字で上書きしてはならない。空の persistent lock file も通常運用では
    unlink しない。
  - `runo lint --scope runs` を実行し、`runs.manifest_table_missing`,
    `runs.manifest_field_missing`, `runs.manifest_field_type` を確認する。診断された
    manifest は SPEC 12.3 と `schemas/manifest.json` に合わせ、最低限次を補完する。
    - `[run]`: `id`, `status`
    - `[origin]`: `case`
    - `[simulator]`: `name`
    - `[launcher]`: `name`
    - `[simulator_source]`: `resolver_mode`, `source_repo`, `git_commit`,
      `build_command`, `executable`, `exe_hash`, `package_version` を string、
      `git_dirty` を boolean で記録する。取得不能な string は `""`、
      `git_dirty` は `false` で補完する。
    - `[job]`: `scheduler`, `job_id`, `submitted_at`
    - `[params_snapshot]`: run 生成時の parameter snapshot。復元できない場合も
      空 table を置き、推測値を作らない。
  - `run.id`, `run.status`, `origin.case`, `simulator.name`, `launcher.name` は、run dir、
    `status/state.json`、元の case、project の simulator/launcher 設定から復元する。
    scheduler 未受付の run では `job_id = ""`, `submitted_at = ""` とし、受付済み
    job の値を空にして schema だけ通すことはしない。
- Validation:
  - `git check-ignore -v --no-index runs/example/.runops-submit.lock` が project の
    `.gitignore` に追加した pattern を表示する。検証のために実 run の lock file を
    作成・変更する必要はない。
  - `runo lint --scope runs` が required table/field/type の issue を報告しない。
  - 利用中の TOML/JSON Schema validator で各 `manifest.toml` が現行
    `schemas/manifest.json` に適合する。
- Rollback:
  - 補完した canonical table/field は以前の v0 release でも TOML data として読める。
    ただし lossless manifest 対応 (`ced2f05`) より前へ戻す場合は unknown top-level
    section と canonical table 内の unknown field を先に backup する。旧版で status
    更新などの manifest rewrite を行うと、それらの extension data は失われ得る。
  - `.gitignore` pattern は残す。claim の有無にかかわらず、rollback 手順として
    `.runops-submit.lock` を一括削除しない。
  - durable claim を認識しない旧版へ戻す前に、全 run の `pending` /
    `accepted:<job_id>` を scheduler と照合して manifest へ reconcile する。未解決の
    claim が一つでもあれば、rollback 後の runtime でもその run を submit しない。
- Human gate:
  - `pending` / `accepted:<job_id>` claim の scheduler 照合と manifest reconcile は
    人間が job identity と受付結果を確認してから行う。

## M0-0007 Structured experiment gate

- Since: unreleased
- Type: breaking-project-state
- Impact: survey bulk submission
- Applies when: `survey.toml` を持つ directory で `runo runs submit --all` を使う。
- What changed: `[research] experiment_id/stage` と `research/experiments.toml` を
  scheduler 呼び出し前に検査する。full stage は EXPAND と review が必須。
- Migration: `runops update-harness` で ledger template を追加し、既存 survey に
  `[research]` を追加する。Research Director で最低 2 候補と selected candidate を記録する。
- Validation: `runo runs submit --all --dry-run` が gate を通り plan を表示する。
- Rollback: survey の `[research]` と ledger は旧版では未使用 metadata として残せる。
- Human gate: candidate 選択と EXPAND decision は人間が確認する。
